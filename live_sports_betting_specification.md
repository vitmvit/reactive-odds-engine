# ТЗ: Реактивный движок обработки live-ставок высокой плотности (Live Sports Betting Processing Engine)

## 1. Обзор системы

Проект представляет собой высоконагруженную реактивную систему для букмекерской конторы. Система принимает поток
спортивных событий от скаутов, на лету пересчитывает коэффициенты ставок с помощью оконных функций и стейт-менеджмента,
а также обрабатывает входящие ставки пользователей с жесткими гарантиями доставки (**Exactly-Once**), защищая бизнес от
арбитража (вилок) и мошенничества.

---

## 2. Архитектура и Движение Данных (REST / Kafka / WebSockets)

### 2.1. Компоненты системы

1. **Match Ingestion Service (Quarkus REST / Producer):** High-Throughput API для приема спортивных событий от внешних
   поставщиков данных.
2. **Bet Ingestion Service (Quarkus REST / Producer):** API для приема ставок от пользователей. Быстро валидирует формат
   и сбрасывает данные в Kafka.
3. **Risk & Odds Engine (Quarkus + Kafka Streams / Consumer + Producer):** Сердце системы. Рассчитывает коэффициенты,
   хранит состояние матчей и подтверждает/отклоняет ставки.
4. **Odds Delivery Service (Quarkus Reactive / WebSockets):** Читает топик с обновленными коэффициентами и транслирует
   их подключенным клиентам через WebSockets.

### 2.2. Схема топиков Kafka

* `match-events` — поток сырых спортивных событий. Ключ: `matchId`. Приоритет: **HIGH**.
* `bet-commands` — поток запросов на фиксацию ставок от пользователей. Ключ: `matchId`. Приоритет: **STANDARD**.
* `active-odds` — поток рассчитанных коэффициентов для трансляции на фронтенд. Ключ: `matchId`.
* `accepted-bets` — подтвержденные ставки, готовые к расчету (выигрыш/проигрыш). Ключ: `matchId`.
* `rejected-bets` — отклоненные ставки (опоздание, нехватка баланса). Ключ: `matchId`.

## 3. Глубокое погружение в Kafka (Гарантии доставки и отказоустойчивость)

### 3.1. Exactly-Once Semantics (EOS)

Обработка ставок в `Risk & Odds Engine` должна быть строго транзакционной. Цикл `Чтение из bet-commands` ->
`Проверка коэффициента в State Store` -> `Запись в accepted-bets/rejected-bets` выполняется в рамках одной *
*Kafka-транзакции** (`isolation.level=read_committed`). Это гарантирует, что при сбое узла ставка не будет обработана
дважды и не потеряется.

### 3.2. Приоритетный Consumer (Защита от арбитража)

Для исключения ситуаций, когда пользователь успевает поставить на старый коэффициент в момент гола (пока событие гола
стоит в очереди), реализуется **Priority Consumer Pattern**:

* Консьюмер в `Risk & Odds Engine` опрашивает топики вручную.
* В цикле `poll()` сообщения из `match-events` выгребаются и обрабатываются в первую очередь.
* Если обнаружено критическое событие (`GOAL`, `RED_CARD`), статус матча в локальном хранилище мгновенно переводится в
  `FROZEN`.
* Все ставки из топика `bet-commands` для этого `matchId`, имеющие timestamp создания позже, чем timestamp гола,
  автоматически отправляются в `rejected-bets`.

### 3.3. Партиционирование по бизнес-ключу

Использование `matchId` в качестве ключа (Kafka Partition Key) гарантирует строгий порядок (FIFO) обработки в рамках
одного матча. Одно и то же событие гола всегда будет обработано *до* ставки, которая прилетела в брокер на миллисекунду
позже.

## 4. Стек технологий и реализация на Quarkus

### 4.1. Реактивное ядро (SmallRye Reactive Messaging / Mutiny)

Использование неблокирующего стека Quarkus для Ingestion-сервисов, чтобы обеспечить обработку десятков тысяч
HTTP-запросов в секунду без создания избыточного количества потоков ОС.

### 4.2. Распределенное состояние (Kafka Streams & RocksDB)

* Текущие коэффициенты, стейт матча (`ACTIVE`, `FROZEN`) и временные окна хранятся в **KeyValue State Store (RocksDB)**.
* Стейт является отказоустойчивым: при падении инстанса Quarkus, новый инстанс восстанавливает RocksDB из Kafka
  Changelog-топика автоматически.

---

## 5. Метрики и Мониторинг (Micrometer / Prometheus)

Для углубленного анализа производительности необходимо настроить сбор следующих метрик через **Micrometer**:

1. **`sports_betting_odds_latency_seconds` (Timer):** Время полного цикла от момента фиксации гола на REST API до
   генерации нового коэффициента в топике `active-odds` (целевое значение: < 50мс).
2. **`sports_betting_transactions_total` (Counter):** Количество закомиченных (`status=committed`) и отмененных (
   `status=aborted`) транзакций Kafka.
3. **`sports_betting_bets_processed_total` (Counter):** Количество обработанных ставок с разбивкой по тегам:
   `status=accepted`, `status=rejected_late`, `status=rejected_balance`.
4. **`sports_betting_rocksdb_memory_bytes` (Gauge):** Объем оперативной памяти, утилизируемый локальными хранилищами
   RocksDB на каждом инстансе Quarkus.
5. **`sports_betting_consumer_lag` (Gauge):** Отставание консьюмеров в топиках `match-events` и `bet-commands`.
