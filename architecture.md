# Архитектура и спецификация Reactive Odds Engine

Высоконагруженная реактивная система для букмекерской конторы, принимающая поток спортивных событий от скаутов,
пересчитывающая коэффициенты ставок в реальном времени и обрабатывающая входящие ставки пользователей с гарантиями
**Exactly-Once**, защищая бизнес от арбитража (вилок) и мошенничества.

---

## 1. Архитектура системы

### 1.1. Микросервисы

| Сервис                      | Стек                              | Роль                                                                                                                                                |
|-----------------------------|-----------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------|
| **match-ingestion-service** | Quarkus REST + Kafka Producer     | Входные ворота для спортивных скаутов. Принимает HTTP/JSON-данные о матче (гол, угловой, карточка) и пересылает в Kafka (`match-events`).           |
| **bet-ingestion-service**   | Quarkus REST + Kafka Producer     | Входные ворота для пользователей. Проверяет авторизацию, валидирует формат ставки и сбрасывает запрос в Kafka (`bet-commands`).                     |
| **reactive-odds-engine**    | Quarkus + Kafka Streams (RocksDB) | Ядро системы. Рассчитывает коэффициенты, управляет заморозкой матчей, проверяет баланс/таймстампы и выносит вердикт по ставкам (принять/отклонить). |
| **odds-delivery-service**   | Quarkus Reactive + WebSockets     | Читает топик `active-odds` и транслирует обновленные коэффициенты тысячам подключенных пользователей через WebSockets.                              |

### 1.2. Топики Kafka

| Топик           | Назначение                                       | Ключ      | Приоритет |
|-----------------|--------------------------------------------------|-----------|-----------|
| `match-events`  | Сырые спортивные и управляющие события           | `matchId` | **HIGH**  |
| `bet-commands`  | Запросы на фиксацию ставок от пользователей      | `matchId` | STANDARD  |
| `active-odds`   | Рассчитанные коэффициенты для фронтенда          | `matchId` | —         |
| `accepted-bets` | Подтвержденные ставки (выигрыш/проигрыш)         | `matchId` | —         |
| `rejected-bets` | Отклоненные ставки (опоздание, нехватка баланса) | `matchId` | —         |

### 1.3. Партиционирование

Использование `matchId` в качестве Kafka Partition Key гарантирует строгий порядок (FIFO) обработки в рамках одного
матча. Одно и то же событие всегда будет обработано до ставки, которая прилетела на миллисекунду позже.

---

## 2. Алгоритмы обработки

### 2.1. Priority Consumer Pattern

Для исключения ситуаций, когда пользователь успевает поставить на старый коэффициент в момент гола, реализуется
приоритетное потребление:

- Консьюмер в `reactive-odds-engine` опрашивает топики вручную через native Kafka API.
- В бесконечном цикле поток принудительно вызывает `consumer.pause()` для партиций топика `bet-commands` и делает
  `poll()` топика `match-events`.
- Только когда высокоприоритетный поток пуст, вызывается `consumer.resume()` для ставок.

Это гарантирует обработку гола до ставки в рамках одного процессорного потока.

### 2.2. Поток обработки спортивных событий

Отвечает за прием сигналов от скаутов, управление заморозкой матча и обновление коэффициентов.

**Пошаговый алгоритм:**

1. Priority Consumer выполняет цикл `poll()`: приостанавливает (`pause`) чтение `bet-commands`, выгребает сообщения из
   `match-events`, при опустошении возобновляет (`resume`) чтение ставок.
2. Движок извлекает `matchId` и проверяет тип события (`eventType`).
3. **Разветвление логики на основе типа события:**

   **Критическое событие (`GOAL`, `RED_CARD`):**
    1. Мгновенная запись в RocksDB: статус матча → `FROZEN`, фиксация `lastCriticalEventTimestamp` (точное время события
       от скаута).
    2. Запуск модуля `OddsCalculator` для пересчета котировок.
    3. Новые коэффициенты и статус `FROZEN` записываются в RocksDB и отправляются в топик `active-odds`.

   **Обычное событие (`CORNER`, `YELLOW_CARD`):**
    1. Статус матча **не меняется** (остается прежним из RocksDB).
    2. Модуль `OddsCalculator` плавно корректирует коэффициенты.
    3. Обновленные данные записываются в RocksDB и отправляются в топик `active-odds`.

   **Управляющее событие готовности линии (`LINE_READY`):**
    1. Статус матча в RocksDB обновляется на `ACTIVE`.
    2. Актуальные коэффициенты и статус `ACTIVE` записываются в RocksDB и отправляются в топик `active-odds`.
    3. **Замер Latency:** После отправки сообщения со статусом `ACTIVE` движок берет текущее системное время сервера,
       вычитает из него исходный таймстамп скаута (`T_скаута`), содержащийся внутри цепочки событий этого матча, и
       отправляет значение в метрику `sports_betting_odds_latency_seconds`.

### 2.3. Поток обработки пользовательских ставок

Работает в режиме **Exactly-Once транзакции**.

| Шаг              | Действие                             | Детали                                                                                                             |
|------------------|--------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| 1. Чтение        | Считывание команды на ставку         | Из `bet-commands` извлекается `BetCommand` (сумма, выбранный исход, `clientTimestamp` — время клика игрока).       |
| 2. Запрос стейта | Чтение текущего состояния матча      | Из RocksDB по ключу `matchId` достаются: статус матча (`ACTIVE`/`FROZEN`) и `lastCriticalEventTimestamp`.          |
| 3. Валидация     | Проверка на «опоздание» (Анти-вилка) | Ставка **отклоняется**, если: статус матча `FROZEN` **ИЛИ** `clientTimestamp >= lastCriticalEventTimestamp`.       |
| 4. Валидация     | Проверка баланса                     | Если баланс пользователя < суммы ставки → отклонение со статусом `REJECTED_BALANCE`.                               |
| 5. Вердикт       | Формирование результата              | Если оба этапа пройдены: ставка фиксирует текущий коэффициент из RocksDB → `AcceptedBet`.                          |
| 6. Запись        | Публикация результата                | Результат записывается в `accepted-bets` или `rejected-bets`.                                                      |
| 7. Фиксация      | Закрытие транзакции (Commit)         | Атомарный коммит смещения (offset) и результатов в Kafka. При сбое транзакция откатывается, исключая дублирование. |

**Принцип валидации:** «Ленивый конвейер» (Lazy Pipeline) — если ставка отклонена на первом этапе (время), проверка
баланса **НЕ вызывается**.

## 3. Расчет и динамическое обновление коэффициентов

Коэффициенты на основные исходы (Победа 1, Ничья, Победа 2 — П1-Х-П2) динамически сдвигаются на основе поступающих
событий и временных интервалов.

### 3.1. Базовая математическая модель

Каждый исход имеет базовую вероятность `P`, где `ΣPᵢ = 1 + margin` (маржа букмекера). Коэффициент равен `K = 1/P`.

1. **При событии `GOAL` для Команды 1:**
    - `P_П1 = min(0.95, P_П1 + Δ_goal)` — вероятность победы Команды 1 резко увеличивается.
    - `P_П2` снижается.
    - `Kᵢ = 1/Pᵢ` → `K_П1` падает, `K_П2` растет.

2. **При событии `RED_CARD` для Команды 2:**
    - Сила Команды 2 снижается из-за численного меньшинства.
    - `P_П1 = min(0.95, P_П1 × 1.25)` — вероятность победы Команды 1 увеличивается.
    - `P_П2` падает.
    - Коэффициенты пересчитываются, прием ставок блокируется (`FROZEN`) до стабилизации линии.

3. **Фактор времени (Затухание):**
    - По мере приближения к 90-й минуте, если счет ничейный, вероятность ничьей (`P_Х`) экспоненциально стремится к
      `1.0`, коэффициенты на победы обеих команд растут.

## 4. Exactly-Once Semantics (EOS)

Обработка ставок выполняется строго транзакционно (`isolation.level=read_committed`):

1. **Чтение (Read):** Извлечение сообщения из `bet-commands` в рамках транзакции.
2. **Запрос состояния (State):** Чтение статуса матча (`ACTIVE`/`FROZEN`) и коэффициентов из RocksDB.
3. **Верификация (Verify):** Проверка условий анти-арбитража (сравнение таймстампов) + валидация лимита суммы ставки.
4. **Запись (Write):** Формирование сообщения с вердиктом и отправка в `accepted-bets` или `rejected-bets`.
5. **Фиксация (Commit):** Смещение (offset) и результаты коммитятся одновременно. При сбое транзакция откатывается
   полностью.

Стейт отказоустойчив: при падении инстанса Quarkus, новый инстанс восстанавливает RocksDB из Kafka Changelog-топика
автоматически.

## 5. Метрики (Micrometer / Prometheus)

### 5.1. `sports_betting_odds_latency_seconds` (Timer)

Сквозной интервал времени от момента фиксации гола скаутом до генерации нового коэффициента:

```
Latency = T_публикации_ACTIVE - T_скаута
```

**Этапы:**

1. Скаут фиксирует гол → событие `GOAL` с таймстампом `T_скаута`.
2. Движок принимает `GOAL`, блокирует ставки, публикует `FROZEN` в `active-odds`.
3. Внешняя математическая модель пересчитывает линию → сигнал `LINE_READY`.
4. Движок применяет котировки, меняет статус на `ACTIVE`, публикует в `active-odds`.
5. Фиксируется `T_публикации`, вычисляется Latency.

**Целевое значение:** < 50мс.

### 5.2. `sports_betting_bets_processed_total` (Counter)

Количество обработанных ставок с тегами: `status=accepted`, `status=rejected_late`, `status=rejected_balance`.

### 5.3. `sports_betting_kafka_transactions_total` (Counter)

Количество транзакций брокера Kafka: `status=committed`, `status=aborted`.

### 5.4. `sports_betting_rocksdb_memory_bytes` (Gauge)

Объем оперативной памяти, утилизируемый локальными хранилищами RocksDB (Block Cache, Memtables) на каждом инстансе
Quarkus. Для предотвращения OOM.

### 5.5. `sports_betting_consumer_lag` (Gauge)

Отставание консьюмеров — разница между Log End Offset в брокере и Current Offset приложения. Мониторится отдельно для
`match-events` и `bet-commands`. Своевременный алерт позволяет предотвратить нарушение SLA до критической деградации.

## 6. Пример сквозного сценария

Забитый гол на 45-й минуте матча:

| Время         | Событие                                                                                                             |
|---------------|---------------------------------------------------------------------------------------------------------------------|
| **00.000 мс** | Команда 1 забивает гол. Скаут жмет кнопку.                                                                          |
| **00.015 мс** | В `match-events` прилетает `GOAL` с `scoutTimestamp = 12:00:00.000`.                                                |
| **00.020 мс** | Priority Consumer обрабатывает гол. В RocksDB: `status = FROZEN`, `lastCriticalEventTimestamp = 12:00:00.000`.      |
| **00.035 мс** | Вилочник жмет «Поставить» на старый коэффициент. В `bet-commands` падает ставка с `clientTimestamp = 12:00:00.250`. |
| **00.040 мс** | Движок читает ставку. RocksDB: `status = FROZEN`. Сравнение: `12:00:00.250 >= 12:00:00.000`.                        |
| **00.045 мс** | Ставка в `rejected-bets` с причиной `REJECTED_LATE`.                                                                |
| **05.000 мс** | Математическая модель пересчитала линию. В `match-events` прилетает `LINE_READY`.                                   |
| **05.010 мс** | Движок обрабатывает `LINE_READY`. В RocksDB: `status = ACTIVE`, новые коэффициенты. Прием ставок возобновлен.       |
